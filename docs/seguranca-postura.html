Segurança · postura

Postura de segurança

Modelo de ameaça e fronteiras de controle do Compre Barato Alagoas — para revisões, scanners e quem avalia se código aberto é compatível com produção.

Resumo: a API de aplicação é pública por desenho (o app Flutter/web é cliente não confiável). O código pode permanecer open source. A proteção não vem de esconder rotas no GitHub; vem de segredos fora do repositório, admin fechado por padrão, limites de abuso, minimização de dados (LGPD) e desligar a UI interativa do OpenAPI em produção. Versão em Markdown no repositório: docs/seguranca-postura.md.

Achado típico de scanner: “API documentada / endpoints visíveis.”
Resposta: o cliente já revela o contrato. Código aberto e docs de produto não substituem autenticação nem limites — e não são vulnerabilidade por si só se os controles abaixo estiverem ativos.

2. O que não é fronteira de segurança

  • Visibilidade do repositório — ocultar o código não remove a API HTTPS do app.
  • Só esconder a URL do admin — sem ADMIN_TOKEN a API admin responde 401 (fail-closed).
  • Swagger/ReDoc em produção — facilita varredura; por isso fica desligado em produção (secção 4).

3. Superfícies e controles

API de aplicação

  • Sem login de conta; identidade de dispositivo opcional (consentimento / listas na nuvem).
  • Token de dispositivo no servidor só como hash com sal.
  • Limite diário de buscas (DAILY_SEARCH_LIMIT).
  • Localização na busca; sem reter trajetos como perfil.

API administrativa (/admin/api/*)

  • ADMIN_TOKEN vazio ⇒ 401 em todas as rotas admin.
  • Comparação em tempo constante (hmac.compare_digest).
  • Vhost admin.<domínio>; cofre Fernet no Redis (status só com fingerprint).

Segredos

ADMIN_TOKEN, SECRET_ENCRYPTION_KEY, token SEFAZ, chave Anthropic e senhas de banco vivem no .env só na VPS (ou painel cifrado) — nunca no git nem no app cliente. API publicada no host apenas em 127.0.0.1:8000 atrás do nginx.

LLM / SEFAZ

  • Entrada do usuário como dados inertes no prompt; fallback determinístico se o modelo falhar.
  • Fan-out SEFAZ limitado; cache Redis reduz repetição.

4. OpenAPI / Swagger em produção

Ambiente/docs, /redoc, /openapi.json
development (local)Ligados
production (deploy)Desligados (404)
EXPOSE_API_DOCS=trueLigados (escape hatch)
EXPOSE_API_DOCS=falseDesligados

O nginx do app só faz proxy de /api e /health — não publica explorador interativo na borda. Endpoints em linguagem de produto continuam em Documentação → API.

Importante: desligar o OpenAPI não esconde o contrato do app; reduz ruído em pentests automatizados e evita consola de exploração desnecessária no mesmo host da API.

6. Checklist rápido

  1. Com ENVIRONMENT=production: GET /docs e /openapi.json → 404.
  2. /admin/api/... sem token → 401.
  3. Nenhum .env real ou token SEFAZ no repositório público.
  4. Redis/Postgres só na rede do compose; API só localhost no host.
  5. CORS_ORIGINS restrito em produção (não * com cenários sensíveis).
  6. Privacidade alinhada ao código (hashes, consentimento para listas na nuvem).

7. Por que open source

  1. Preços já são públicos (SEFAZ-AL); o valor está na ponte segura e na UX honesta.
  2. Alegações de LGPD ficam auditáveis.
  3. Fechar o GitHub não fecha a API HTTPS do app.

Restrito ao time (repo privado ou só VPS): segredos de operação e notas internas — não este desenho.

8. Limitações honestas

  • Root na VPS ainda lê memória e .env no disco (HSM/KMS seria outro patamar).
  • Sem Redis a API não sobe (falha rápida).
  • Este texto não substitui pentest formal nem laudo de DPO externo.
